# Rust's cancellation gap forces a leak-first io_uring v0

Rust's async cancellation model has no native answer for completion-based I/O, and the ecosystem's real fix has been architectural, not linguistic: every production Rust io_uring runtime — tokio-uring, compio, monoio, glommio — survives by transferring buffer ownership to the kernel and treating a dropped future as "abandoned, to be cleaned up whenever the kernel eventually says so," never as "stopped." The language-level alternative that would make this safer by construction — `AsyncDrop`, `poll_cancel`, linear/unforgettable types — remains unstable, contested, and by the clearest 2025 estimate ("possibly not before 2027") years from shipping. Meanwhile, the verification tools built for exactly this class of unsafe, FFI-adjacent, ownership-sensitive code — loom, Miri, Kani — are **not used in CI by any of the three major Rust io_uring runtimes examined** (tokio-uring and compio confirmed directly from their workflow files; monoio confirmed absent from its README), even though Tokio's own non-io_uring core runs both Miri and loom. The implication for a new io_uring runtime project is that a responsible v0 cannot wait for the language to solve cancellation safety, must copy the specific "leak-until-real-completion" pattern the whole ecosystem converged on independently, and should treat verification tooling as a differentiator it adds precisely where competitors have not — on the pure-Rust slab/buffer bookkeeping layer that Miri, Kani, and loom *can* actually reach, since none of them can observe the kernel side of the ring at all.

## The cancellation problem is not ergonomic, it is a soundness hole unique to completion I/O

Without Boats' 2020 essay "Notes on io-uring" remains the clearest statement of why this is a real bug class, not a style complaint: Rust's async model treats cancellation as implicit and silent — dropping a future, or simply stopping polling it, is cancellation, and under a *readiness*-based API like epoll that's harmless because the kernel never held a buffer pointer to begin with. Under a *completion*-based API, the kernel has already been handed a live pointer and performs the read/write asynchronously and independently of Rust's control flow; if the future is dropped and its buffer freed or reused before the kernel's completion queue entry (CQE) arrives, the result is a genuine data race or use-after-free ([Notes on io-uring](https://without.boats/blog/io-uring/)). Boats explicitly rejects the two tempting fixes: blocking in `Drop` until the kernel finishes is "unsound and a non-starter" because Rust permits leaking any value, so a destructor can never be relied upon to run at all, and even when it does run, blocking a thread on unwanted I/O breaks timeout semantics outright; and merely `Pin`-ning the buffer (a proposal attributed to Taylor Cramer) only stops the memory from moving or being freed, not from being concurrently read or written by the Rust side while the kernel still touches it — still a data race ([Notes on io-uring](https://without.boats/blog/io-uring/)). His conclusion — "the kernel must own the buffer" because Rust's type system has no other way to model an external, uncancellable actor touching memory on its own schedule — is the single load-bearing design constraint that every subsequent runtime implements. His own prototype, Ringbahn (2020, now abandoned since ~2021), built this out concretely: an `Event::prepare` contract that "passes ownership" of the buffer to the kernel, and a `Completion` object with three states (Submitted/Completed/Cancelled) where cancellation swaps the waker for a **cancellation callback** that runs cleanup only once the kernel's real completion eventually lands — avoiding both use-after-free and a permanent leak ([Ringbahn II](https://without.boats/blog/ringbahn-ii/)). Notably, even this careful design produced real bugs in practice: Boats' own retrospective, "Two Memory Bugs From Ringbahn," documents a double-free and a use-after-free he introduced while implementing exactly this cancellation path — direct evidence that the pattern is conceptually sound but mechanically unforgiving ([Two Memory Bugs From Ringbahn](https://without.boats/blog/two-memory-bugs-from-ringbahn/)).

Every mainstream runtime subsequently converged on the same answer by necessity. tokio-uring's design doc states plainly that operation futures are `!Send`, buffers (`IoBuf`/`IoBufMut`) pass ownership into the kernel and come back only on completion, and the driver keeps in-flight operation state — including buffers and file descriptors — in a slab until the real CQE arrives, "since the kernel may still be using that data"; dropping a submitted-but-incomplete op moves it to an `Ignored` lifecycle state rather than freeing anything, and a best-effort `ASYNC_CANCEL`-style request is submitted, with the explicit caveat that "cancellation is asynchronous and best-effort, the operation may still complete" ([tokio-uring DESIGN.md](https://docs.rs/crate/tokio-uring/latest/source/DESIGN.md)). compio's driver documentation is equally blunt that cancellation "is not reliable. The underlying operation may continue, but just don't return from `Proactor::pop`" ([compio-driver source](https://docs.rs/crate/compio-driver/0.12.2/source/src/buffer_pool.rs)), and monoio exposes an explicit `Canceller`/`cancelable_accept` API that requires the caller to re-await the original future after cancelling to reclaim the buffer, with its own design docs acknowledging cancellation via `async-cancel` is "only best-effort," including documented cases where an accepted TCP connection can simply be lost ([monoio io-cancel.md](https://geedge-git.gfw.report/mesalab_git/zhangyang/monoio.git/plain/docs/zh/io-cancel.md)). The Linux kernel interface itself backs this up: `IORING_OP_ASYNC_CANCEL` only *requests* cancellation and provides no guarantee the targeted operation is stopped before completion ([io_uring_cancelation(7)](https://www.man7.org/linux/man-pages/man7/io_uring_cancelation.7.html)). A 2024 Tonbo blog post, "Async Rust is not safe with io_uring," sharpened the residual risk with a concrete, reproducible bug: racing `listener.accept()` against a timeout via `select!` on monoio's io_uring backend silently leaks the accepted TCP connection — because the accept syscall can complete in the kernel before the cancellation SQE is even submitted — while the identical code on monoio's epoll backend does not leak, isolating the defect to completion semantics specifically ([tonbo.io](https://tonbo-io.pages.dev/blog/async-rust-is-not-safe-with-io-uring)). Tonbo names glommio, monoio, and compio as all exhibiting this class of issue; Without Boats himself, replying on Hacker News, argued the fault lies in specific flawed runtime APIs rather than in async Rust as a language, while a commenter in the same thread countered that even a careful cancellation-callback design can still leak a file descriptor if the kernel's accept completes before the cancel SQE reaches it — underscoring that this remains best-effort "all the way down," not a solved problem even in the most careful implementations ([HN discussion](https://hn.jakechampion.name/item/41992975)).

## The lang-team track exists but is years from shipping anything a v0 can depend on

There is no merged `rust-lang/rfcs` RFC for AsyncDrop; what exists instead is compiler-team Major Change Proposal #727, accepted via FCP in March 2024, with the `AsyncDrop` trait and drop glue landing behind the unstable `#![feature(async_drop)]` gate and no stabilization announced as of the most recent evidence found — a community workaround crate dated January 2026 is itself proof the native feature still isn't usable on stable ([compiler-team#727](https://github.com/rust-lang/compiler-team/issues/727); [Unstable Book: async-drop](https://doc.rust-lang.org/nightly/unstable-book/language-features/async-drop.html)). Several sub-components of that MCP are explicitly stalled: "suspending unwinding tasks" has "no work happening right now," and a `Forgettable` trait exists only on a branch. The wg-async roadmap itself concedes the *current* model — synchronous, forced cancellation at any `.await` point via ordinary `Drop` — "leads to a lot of bugs," and proposes a "shiny future" of **voluntary/cooperative cancellation** (a queryable flag the task can check rather than forced teardown), but this is explicitly aspirational design space with no committed timeline, and the roadmap even notes that cancelling via AsyncDrop alone is of unclear value "beyond simply not implementing AsyncDrop" ([wg-async roadmap: scopes](https://rust-lang.github.io/wg-async/vision/roadmap/scopes.html)). Without Boats' own thinking evolved in parallel: his 2024 post "Asynchronous clean-up" de-emphasizes AsyncDrop as the primary mechanism and instead proposes `poll_cancel` (making cancellation itself a cooperative, pollable operation) plus a `do ... final` block for guaranteed cleanup on every exit path — explicitly framing `poll_cancel` as the *near-term*, shippable piece, while treating **linear types** (an `AsyncDrop`-style "undroppable" scheme credited to Niko Matsakis, plus a `Leak` auto-trait) as the real long-term guarantee, which he estimates is "possibly not before 2027" ([Asynchronous clean-up](https://without.boats/blog/asynchronous-clean-up/)). A 2022 internals.rust-lang.org thread literally titled "Add `poll_cancel` to Future" ran for several months with substantive back-and-forth (SkiFire13 pointed out that buffer-borrowing io_uring code needs guaranteed destructor execution for soundness, which `poll_cancel` alone doesn't provide) and then auto-closed after 90 days of inactivity with no resolution — the community's working answer was not a language fix but the library-level ownership-transfer pattern already shipping in tokio-uring ([internals thread](https://internals.rust-lang.org/t/add-poll-cancel-to-future/16050)). A newer, parallel 2025–2026 thread of discussion (Niko Matsakis's `Forget`/`Destruct`/`Move`/`Pointee` auto-trait hierarchy, a tracked 2026 Rust Project Goal on "Immobile types and guaranteed destructors," and a RustConf 2025 talk naming "unforgettable types" as one of several competing candidate fixes for "cancel-correctness" bugs) confirms the field is still actively negotiating first principles, including open internal disagreement over whether `Move` should even be a supertrait of `Destruct` ([2026 goal: move-trait](https://goals.rust-lang.org/2026/move-trait.html)). The upshot for a v0 scope: nothing stable is coming soon enough to lean on, and the "shiny future" cooperative-cancellation model, even once available, won't retroactively make a naive `&mut [u8]`-borrowing io_uring API sound — ownership transfer is required regardless of what the language eventually ships.

## Verification tooling exists for exactly this problem — and the ecosystem is not using it

Of the three tools evaluated, each targets a different, non-overlapping slice of the problem, and none of them can touch the actual kernel-facing half of an io_uring runtime. Loom is a permutation-based model checker for multi-threaded concurrent Rust under the C11 memory model; it is built for cross-thread data-structure bugs (its own example API is `thread::spawn`/`Arc`/`AtomicUsize`), requires code under test to use loom's own `UnsafeCell`/atomic shim types rather than `std` ones to be checked at all, and Miri's own README explicitly recommends loom as the complementary tool for "complicated atomic code" ([tokio-rs/loom](https://github.com/tokio-rs/loom); [rust-lang/miri README](https://github.com/rust-lang/miri)). That makes loom a poor fit, by construction, for a single-threaded, thread-per-core completion-I/O reactor, where the core hazard is buffer/Op lifetime across submission and completion rather than thread interleaving — it only becomes relevant if a runtime adds cross-thread work-stealing or shared ring state, which this research separately argues a v0 should avoid anyway. Miri is an interpreter that catches out-of-bounds access and use-after-free, invalid use of uninitialized memory, intrinsic-precondition violations, misalignment, type-invariant violations, (experimentally) data races and aliasing-model violations — but it fundamentally fakes or blocks host access, cannot execute real syscalls, explicitly calls networking "unsupported," and marks its one FFI escape hatch (`-Zmiri-native-lib`) as itself unsound ([rust-lang/miri README](https://github.com/rust-lang/miri)). That means Miri can validate only the pure-Rust bookkeeping around io_uring — slab indexing, `Op` state-machine transitions, buffer-pool reuse logic — tested against mocked completions, never the actual `io_uring_enter` handoff; Tokio's own CI confirms this pattern by running Miri on its core but specifically skipping tests that call `epoll_create1`, a syscall Miri cannot execute. Kani is a bit-precise bounded model checker (not an exhaustive proof tool) that AWS has applied extensively to exactly the adjacent problem class — Firecracker's I/O rate limiter and VirtIO queue parsing — by treating untrusted input (guest memory, in that case) as `kani::any()`-generated arbitrary bytes fed through an unsafe raw-pointer path; this found five bugs in the rate limiter alone, including a rounding error that let a VM exceed its configured I/O throughput by up to 0.01%, and separately found crashes from adversarial VirtIO queue placement ([Kani Firecracker blog post](https://model-checking.github.io/kani-verifier-blog/2023/08/31/using-kani-to-validate-security-boundaries-in-aws-firecracker.html)). That is a strong structural analogy for an io_uring runtime's completion-slab index arithmetic under adversarial CQE ordering — but no source found documents Kani (or any BMC tool) ever having actually been applied to an io_uring Rust runtime.

The gap between "these tools exist and would help" and "anyone actually runs them" is stark and directly verified in this research, not inferred: a direct fetch of tokio-uring's CI workflow (`tokio-rs/tokio-uring/.github/workflows/ci.yml`) shows only `check`, `clippy`, plain `cargo test`, `test-docs`, `fmt`, and `docs` jobs — **no Miri, no loom** ([tokio-uring ci.yml](https://raw.githubusercontent.com/tokio-rs/tokio-uring/master/.github/workflows/ci.yml)). A direct fetch of compio's test workflow (`compio-rs/compio/.github/workflows/ci_test.yml`) shows only `cargo nextest run` and `cargo test --workspace --doc` across a build matrix, with a nightly toolchain entry used solely to gate a Cargo feature flag — **no Miri, Loom, Valgrind, or ASan** ([compio ci_test.yml](https://raw.githubusercontent.com/compio-rs/compio/master/.github/workflows/ci_test.yml)). monoio's README contains no mention of Miri, loom, sanitizers, fuzzing, or Valgrind anywhere. This stands in direct contrast to Tokio's own (non-io_uring) core, which runs a dedicated `loom.yml` workflow (capped at `LOOM_MAX_PREEMPTIONS: 2`) and a Miri job in CI for its epoll-based internals — even as a Tokio issue notes some of `tokio-util`'s loom-based tests, such as for `CancellationToken`, exist in the codebase but "are not being run in CI." No RUSTSEC advisory specific to io-uring/tokio-uring/compio/monoio/glommio buffer-lifetime or cancellation issues was found in this research pass, which most plausibly reflects that the failure mode (best-effort cancellation leaking a resource) is treated by maintainers as a documented architectural limitation rather than a patchable CVE — the fixes are slabs and `Ignored` states, not version bumps.

## A thread-per-core, leak-until-real-completion v0 is the architecture the whole ecosystem already validated

Every runtime surveyed — tokio-uring, monoio, compio, glommio — independently rejected cross-thread work-stealing in favor of thread-per-core (or current-thread) execution, and the stated reasoning ties directly back to the cancellation problem: `!Send` operation futures tied to kernel-owned buffer state are naturally confined to one thread, and multithreading is achieved by running N independent single-threaded runtimes rather than one work-stealing scheduler that would need to reason about cross-thread completion delivery. tokio-uring's design doc states this was a deliberate tradeoff — work-stealing was considered and rejected because "the required synchronization adds overhead," with target users benefiting more from "direct control over how load is balanced" than automatic rebalancing ([tokio-uring DESIGN.md](https://docs.rs/crate/tokio-uring/latest/source/DESIGN.md)). Glommio's Datadog-authored introduction frames the same choice around eliminating locks entirely: "the biggest advantage of this model is that locks are *never necessary*," because exactly one thread ever touches a given shard's data and tasks "run to completion" without fear of mid-operation preemption by another thread on the same core ([Introducing Glommio](https://www.datadoghq.com/blog/engineering/introducing-glommio.md)). The known, acknowledged cost of this design — one every v0 builder should budget for, not discover in production — is poor load balancing under skew: monoio's own docs warn that "very unbalanced workloads can underuse cores and perform worse than Tokio," and Apache Iggy (a real production adopter that migrated from Tokio to compio for a thread-per-core rewrite) separately reported a concrete, Rust-specific footgun of the shared-nothing model: holding `RefCell` borrows across `.await` points in a thread-per-core, shared-nothing environment causes runtime panics ([DEV Community: Apache Iggy](https://dev.to/sospeter/how-apache-iggy-ditched-tokio-for-thread-per-core-iouring-and-what-it-cost-them-3m75)). Iggy chose compio over monoio specifically for its broader io_uring feature coverage and its driver/executor separation, and separately flagged glommio as "effectively unmaintained" after its original author departed — a concrete maintenance-risk data point against depending on glommio, even though its architectural rationale (lock elimination via single-thread ownership) is sound and worth emulating directly rather than importing as a dependency.

For the owned-buffer API specifically, the convergence is total and the mechanism is simple: because io_uring hands the kernel a raw pointer that must remain valid until a CQE arrives, a borrowed `&mut [u8]` cannot express "an external, uncancellable party may touch this memory on its own schedule," so all three production runtimes require the caller to pass *ownership* of the buffer (via `IoBuf`/`IoBufMut`-style traits) into the operation, with the runtime holding it in a driver-owned slab until real completion — this is also, independently, the fastest interface, since "the fastest interfaces on io-uring are the buffered interfaces, the unbuffered interfaces make an extra copy" ([Notes on io-uring](https://without.boats/blog/io-uring/)). "Leak-on-cancel" is this report's own descriptive shorthand for the pattern, not a term any primary source uses verbatim — the mechanism is consistently described as deferred/orphaned resource release (buffer or fd kept alive until the real CQE lands, then cleaned up), which only becomes a genuine permanent leak if nothing ever polls for that stray completion. `rustfs-uring`'s explicit `without_cancel_on_drop` configuration option and Tokio's own dedicated cancel-on-drop regression test for `openat` both confirm the community treats this as a deliberate, tested design surface rather than an accepted bug.

## A minimal, defensible v0 scope and what the data says about which features actually matter

Weighing payoff against complexity across the architecture notes, the clearest conclusion is that the features earning their complexity for a v0 are: (1) a single-threaded reactor per core with `!Send` tasks and no work-stealing — the one architectural choice every runtime treats as foundational, and the only one credited with a cited multi-core scaling number (monoio's own benchmarks claim ~2x Tokio's throughput at 4 cores and ~3x at 16, though this is vendor-published and not independently verified); (2) an owned-buffer API (`IoBuf`/`IoBufMut`-style) as the only sound interface to single-shot Read/Write/Accept/Recv ops, which is simultaneously the safety requirement and, per Boats, the faster interface; and (3) adaptive submission batching (deferring `io_uring_enter` until the submission queue fills or the driver is about to park), which compio's driver implements as actual code with no kernel-privilege or resource-registration cost — purely a scheduling decision in the submit/park loop. Leak-on-cancel (submit a best-effort `ASYNC_CANCEL`, hold the buffer in a driver slab, run cleanup only on real CQE arrival) is the only sound cancellation strategy available on stable Rust today and should be adopted outright, with an explicit test (mirroring Tokio's `complete_ops_on_drop`/cancel-on-drop pattern) asserting no double-free and no leaked fd across a drop-during-flight path.

SQPOLL, registered buffers/files, and multishot accept/recv are all defensible deferrals, and the research is specific about why. SQPOLL requires a dedicated kernel polling thread *per ring*, which directly conflicts with a thread-per-core design's goal of using every core for application work — one SQPOLL ring per core multiplies kernel CPU cost linearly with core count — and pre-5.13 kernels additionally require `CAP_SYS_NICE` or root ([io_uring_sqpoll(7)](https://man7.org/linux/man-pages/man7/io_uring_sqpoll.7.html)); no evidence was found that either compio or monoio enable it by default, and no benchmark comparing it on/off for either runtime exists in the sources gathered. Registered buffers/files and multishot ops add resource-lifecycle complexity (registration/unregistration, fixed-slot allocation, and for multishot recv specifically, buffer-ring refill logic to avoid `-ENOBUFS` termination) for a benefit the evidence suggests is secondary to the proactor-plus-thread-per-core foundation — neither feature was found in active use in the specific monoio/compio driver files inspected. On the performance question more broadly, the benchmark evidence argues for caution about *expecting* dramatic networking gains at all in a v0's target range: io_uring's networking advantage over epoll is typically 0–20% and frequently reverses (epoll winning at 8–16KB message sizes in the uWebSockets author's tests, attributed to io_uring's per-socket buffers exceeding L2/L3 cache on older hardware), while a tokio-rs/io-uring maintainer issue (#291) found a naive single-ring io_uring receiver losing to multi-threaded Tokio by 2x until `SO_REUSEPORT` sharding was added, at which point the two converged exactly — a maintainer-confirmed instance of "the gap was a threading artifact, not an epoll-vs-io_uring difference." Even Jens Axboe's own 2023 writeup on io_uring networking "does not attempt to be a case study in gains achievable by switching from epoll," framing the real payoff as high-connection-count, high-request-rate production workloads (he cites Meta's Thrift) rather than a general claim — which argues that a v0 targeting a small (1–4 core) deployment should expect parity with well-tuned `SO_REUSEPORT`-sharded Tokio, not a clear win, and should not let a disappointing initial benchmark undermine confidence in the architecture.

On verification tooling specifically, the responsible move for a new project is to do what the incumbents conspicuously do not: split the unsafe surface into a pure-Rust layer (buffer slab allocation/indexing, Op state-machine transitions, waker bookkeeping) that can be fuzzed and run under Miri with mocked completions, exactly mirroring how Tokio's own CI runs Miri while explicitly skipping syscall-touching paths it cannot execute — and a syscall-adjacent layer (the actual SQE/CQE submission path) that Miri and Kani cannot reach and must instead be exercised by integration tests under real kernels at elevated queue depth specifically to force exhaustion paths (submission-queue-full, `-ENOBUFS` on multishot, `-ECANCELED` races) that only appear under load. Loom is lower-priority for a genuinely single-threaded v0 but becomes directly relevant the moment any shared state crosses a thread boundary (e.g., a cross-core wake mechanism), and should be adopted at that point rather than retrofitted later. Kani's Firecracker precedent — treating adversarial input as `kani::any()`-generated arbitrary bytes through an unsafe pointer path — is a concrete, reusable template for the completion-slab index arithmetic specifically, even though no prior io_uring Rust project has tried it, which makes it a genuine differentiator rather than catching up to an existing practice. Separately, Jens Axboe's own guidance that `IORING_SETUP_COOP_TASKRUN` (and `DEFER_TASKRUN`, kernel 6.1+) "has shown to yield very nice benefits" for applications that redesign their completion-handling loop around it is worth adopting early since it is a flag, not an architecture change, while multishot/registered-buffer adoption should wait until profiling a real workload justifies the added lifecycle complexity.

## Conclusion

The most counterintuitive finding here is the inversion between effort and risk: the hardest-sounding problem — io_uring cancellation safety — already has a converged, implementable answer (ownership transfer plus deferred cleanup) that costs nothing to adopt and requires no bet on unstable language features, while the tooling that exists specifically to catch mistakes in implementing that answer (Miri, Kani, loom) is sitting unused across the entire production ecosystem, representing the actual low-hanging opportunity for a new project to differentiate on correctness rather than performance. The practical implication is that a v0 should spend its scarce engineering budget on getting the leak-on-cancel/owned-buffer pattern right and verified at the Rust layer — via Miri on mocked-completion slab logic, Kani on adversarial-CQE-ordering index arithmetic, and load-testing at high queue depth to force the exhaustion paths real kernels only reveal under pressure — rather than on SQPOLL, registered buffers, or multishot ops, whose performance payoff is unproven at small core counts and whose complexity is precisely the kind that has produced real, if informally documented, resource-leak bugs even in the most careful prior art (Ringbahn's own author-introduced double-free, the monoio accept-leak Tonbo reported). The language-level fix that would make all of this unnecessary — `poll_cancel`, linear types, guaranteed destructors — is real, actively worked on, and explicitly not coming within the lifetime of a v0 release.
